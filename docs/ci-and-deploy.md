# Build pipeline, CI, smoke testing, deploy and validate

> Moved verbatim from `CLAUDE.md` on 2026-09-05.

## Build pipeline

Two producers, and they are not interchangeable. This repository's CI ([`.github/workflows/build-console.yml`](.github/workflows/build-console.yml)) publishes `ghcr.io/scality/artesca-vss-console:latest` + `:sha-<short>` on every push to `main` — that is the image a lab deploy pulls when the operator has no checkout. For the edit-and-redeploy loop, `isv-labs:scripts/build-console-image.sh` builds **this checkout** laptop-side with a Docker-compatible daemon (OrbStack, Docker Desktop) and sideloads the result onto the node; it picks the two apart by `CONSOLE_SOURCE_MODE`. Persistent buildx layer cache at `${TMPDIR:-/tmp}/nvidia-vss-console-buildx-cache` (outside the repo; bust with `rm -rf`, override with `BUILDX_CACHE_DIR`). Warm rebuilds drop from ~30s to under 10s when source is unchanged.

**Both jobs run on `ubuntu-24.04`, pinned.** On Ubuntu 26.04 (what `ubuntu-latest` became) `npx playwright install --with-deps chromium` fails with "Playwright does not support chromium on ubuntu26.04-x64" (runs 40723172002 and 40723961222, 2026-10-28), and with the `ci` job red no image is pushed. Move the pin only with a Playwright that supports the newer image.

**Monaco is served by the app, not by a CDN, and that costs a build step.** `@monaco-editor/react` fetches Monaco from `cdn.jsdelivr.net` unless told otherwise — and resolves whatever version the CDN currently serves, not the pinned one — so on a node without egress the editor never loads. [`scripts/copy-monaco.mjs`](scripts/copy-monaco.mjs) copies `monaco-editor/min/vs` into `public/monaco/vs` (gitignored, ~13 MB) from the `prebuild`, `predev` and `pretest:e2e` hooks; Playwright spawns `npx next dev` directly rather than through `npm run dev`, which is why `predev` alone is not enough. `postinstall` would cover all three and is deliberately unused — the Dockerfile installs with `--ignore-scripts`.

Two rules follow, both silent when broken:

- **Import the editors from [`src/components/monaco.ts`](src/components/monaco.ts), never from `@monaco-editor/react`.** A direct import gets the CDN back. [`tests/unit/monaco-single-entry.test.ts`](tests/unit/monaco-single-entry.test.ts) fails if one appears.
- **`paths.vs` must be origin-qualified**, not the bare `/monaco/vs`. Monaco runs each language service in a worker created from a blob URL, which has no base for a relative path to resolve against. The editor still renders and still accepts typing either way — what disappears is JSON validation, formatting and hover on the two `language="json"` editors.

[`tests/e2e/monaco.spec.ts`](tests/e2e/monaco.spec.ts) holds both ends of that: it aborts every request to the CDN, then asserts the editor renders *and* that a language worker answers. Neither failure is visible on a laptop, which has egress.

The host-ctr import flow on Rocky 8 nodes is fragile (libdl.so.2-class glibc 2.28 mismatches with importer containers). Catch breakages locally with [`isv-labs:scripts/verify-ctr-compat.sh`](isv-labs:scripts/verify-ctr-compat.sh) — spins up (or reuses) a Rocky 8 amd64 VM `nvidia-vss-ctr-lab`, installs containerd, and reproduces the bind-mount flow with a tiny amd64 tarball. First provision ~35s; reruns ~6s. Override `IMPORTER_IMAGE=...`; `alpine:3.19` is a reliable failure canary.

## CI — the E2E env, and who hears a red run

**The E2E step has to declare its own environment.** It runs a production `next start`, which reads no `.env` file, so anything the app needs is on the step or absent. Two variables decide whether a spec can reach a page at all, and neither can be inferred from a local run — locally Playwright spawns `next dev` and reuses a server that took both out of `.env.local`:

- **`AUTH_SECRET`** — Auth.js requires a cookie-signing secret under `NODE_ENV=production`. `AUTH_SECRET` is the name it reads; the `NEXTAUTH_`-prefixed spelling is consulted by nothing, so a deploy setting only that gets a pod that refuses every request while `src/instrumentation.ts` logs `missing env vars: AUTH_SECRET`. The value on the step is a throwaway for a localhost server torn down with the job.
- **`CONSOLE_DISABLE_AUTH`** — the specs stub `/api/auth/session` with `page.route`, a browser-level intercept `src/proxy.ts` never sees, so a guarded page needs a real server-side session. Without the bypass every one answers `307` to `/sign-in` and each spec fails against whatever page it opened, which reads as a Monaco, cameras and diagnostics fault all at once rather than as an auth problem.

⚠ **A missing secret used to be survivable, and that is why this hid.** On `@auth/core` 0.37.4 it let requests through; 0.41.3 refuses. The last green run before the bump logged `MissingSecret` **1421 times** and still reported 76 passed — so the misconfiguration long predated the version that exposed it. [`tests/unit/e2e-workflow-env.test.ts`](tests/unit/e2e-workflow-env.test.ts) now reads the required-env list out of `src/instrumentation.ts` and asserts the workflow sets each one, so adding a required variable fails a unit test instead of 26 E2E specs.

Consequence worth knowing: no spec exercises a genuine session. `k8s/11-configmap-env.yaml` also sets `CONSOLE_DISABLE_AUTH=true`, so the deployed console is in the same posture — the sign-in gate is covered only by `auth.spec.ts` against the sign-in page itself.

⚠ **A local E2E run can be green against a cluster instead of your code.** `reuseExistingServer` is on outside CI, so Playwright attaches to whatever holds its port rather than starting `next dev` — and `:8800` is the port an operator forwards the in-cluster console to. Measured 2026-08-14: with a `kubectl port-forward` to the Pyramid showroom console up, all 8 specs of `sg-whitelist.spec.ts` passed **against the deployed pod**, including one written that minute for a page change that pod had never seen. Nothing looked wrong; the browser-level `page.route` stubs make most specs pass against any console. `PORT` therefore defaults to `8899` locally and `:8800` only under `CI`, where no port-forward exists; `E2E_PORT` overrides either. If a spec ever passes that you expected to fail, check what is listening (`lsof -nP -iTCP:<port> -sTCP:LISTEN`) before believing it.

**Nothing in the workflow can send mail, so the alarm is laptop-side.** `scality/artesca-vss-console` is **not** in the `github-pool` WIF allowlist and the repository has **no Actions secrets or variables at all**, so a job here reaches neither Secret Manager nor the Gmail token. ⚠ The same gap silently disables the Sentry source-map upload in `build-and-push`: its `google-github-actions/auth` step reads `secrets.GCP_WIF_PROVIDER`, which does not exist, and is `continue-on-error: true`.

[`scripts/ci-alert.py`](scripts/ci-alert.py) therefore polls from a LaunchAgent (`com.scality.console.ci-alert`, every 15 min) and mails through `isv-backend/scripts/notify.py`, so a red console build lands in the same `[ISV job-failed]` / `X-ISV-Alert` grammar as the VM fleet. It reports four states, and the third is the one a "did the newest run fail" check gets wrong: `failure`, `recovered`, **`unverified`**, and **`covered`**. `unverified` is a run cancelled with nothing executed, or a HEAD with no run at all and no ancestor's run covers it. During the GitHub Actions outage of 2026-08-06 seven consecutive pushes created no run, and reading only the newest run's conclusion reports the last green one while main is unchecked. `covered` is the case that used to read as `unverified` for 39 hours (HEAD d2fecc9, 2026-09-23..25): `build-console.yml`'s `paths:` filter means a commit outside `src/**`/`tests/**`/etc. (a CLAUDE.md-only commit, say) never creates a run at all. The script walks up to 20 ancestor commits on `main` for the newest one with a completed run, diffs it against HEAD via `gh api .../compare`, and matches the changed files against the workflow's own `paths:` globs (parsed at runtime from the checked-out workflow file — no PyYAML). No match means HEAD inherits that ancestor's conclusion (green stays green, a failing ancestor still alerts); any match falls back to plain `unverified`, as does any failed API call along the way. Mail is deduped on (state, sha), recovery mails once, and the check reports **its own** failure rather than going quiet, since a poller that stops polling is indistinguishable from a green main. `--selftest` covers the classifier, the glob matching and the coverage logic offline; `--dry-run` polls and writes nothing.

## Smoke testing

[`scripts/smoke-test-console.sh`](scripts/smoke-test-console.sh) applies [`k8s/`](k8s/) against OrbStack's built-in K8s (`context: orbstack`) with the image swapped to `nginxinc/nginx-unprivileged:alpine`, probes removed, PVC rebound to `local-path`, and dummy Secrets created in-script. It is the only script here, because it is the only one that tests **this repository's** own artifacts. It catches manifest-level bugs (missing ConfigMap/Secret refs, broken Service selectors, PVC stuck Pending, RBAC binding to non-existent ns, port-name collisions) in ~30s, against the ~10 min remote rebuild+scp+apply cycle. Idempotent, cleans up via `kubectl delete ns`.

It exits 0 against OrbStack (verified 2026-08-06). A `test-footage-data` PVC that nothing creates is what used to make it unpassable, so `30-test-footage.yaml` is in `k8s/kustomization.yaml`'s `resources` list and has to stay there: `20-console.yaml` mounts that PVC, and Kubernetes has no optional PVC volume, so the pod does not schedule without it.

Caveat: it does **not** test app behavior. End-to-end testing needs a real deploy.

## Deploy + validate

Both live in **isv-labs**, because both are coupled to a lab instance — they resolve its directory, SSH to its node, and read its state:

```bash
isv-labs:scripts/deploy-console.sh   --instance <name>   # build or pull, sideload, kubectl apply
isv-labs:scripts/validate-console.sh --instance <name>   # pod Ready + /api/health/self + recording canary
```

The flow is idempotent — reruns re-apply the manifests and pick up image-tag changes. Nothing in this repository deploys itself; copies of those scripts lived here until ISVD-564 and none of them ran, because they source libraries only isv-labs has.

## Observability (Sentry)

Errors + tracing + masked session replay report to Sentry org **scality-3i**, project **scality-vss-console-ui** (region `de.sentry.io`). Full runbook: [`docs/console-sentry.md`](docs/console-sentry.md).

- **The SDK is an optional install, and absence is a different axis from "no DSN".** `@sentry/nextjs` is in **no** dependency field, because it pulls `@sentry/cli` under **FSL-1.1-MIT** — source-available, not open source — and this repository is public. Measured: declared, `node_modules` holds 2 FSL packages; undeclared, 0. Opt in with `npm run enable-telemetry`; images opt in with `--build-arg WITH_TELEMETRY=1` (CI and `isv-labs:scripts/build-console-image.sh` both pass it, so lab images keep reporting). ⚠ `optionalDependencies` does **not** do this — npm installs those by default; nor does an optional `peerDependency`, which keeps a clone clean but is then **impossible to install** (`--no-save`, `--force`, `--include=peer` all leave it absent, and the lockfile holds no entry). Both measured on npm 11.12.1. That is why the opt-in is `npm install --no-save` against an exact pinned version, and why that version is the only thing pinning the resolution — there is no lockfile entry and `npm audit` on a default clone cannot see it.
- **[`telemetry-optional.cjs`](telemetry-optional.cjs) is the single presence check**, because three resolvers must agree and each fails differently: `next.config.js` (the build — it aliases the specifier to [`src/lib/telemetry-noop.ts`](src/lib/telemetry-noop.ts) via `turbopack.resolveAlias` when absent), `vitest.config.ts` (the tests — vitest does **not** honour that alias; without its own, 3 files and 5 tests fail on a clone with no SDK), and `tsc` (suppressed with `@ts-ignore` on one import — `@ts-expect-error` is wrong, since an unused directive is itself an error when the SDK *is* present). [`src/lib/telemetry.ts`](src/lib/telemetry.ts) is the only file naming the package; everything else imports from it, which turns absence into one resolution problem instead of seven. [`tests/unit/telemetry-optional.test.ts`](tests/unit/telemetry-optional.test.ts) pins all of it, including that the stub still exports every `Sentry.*` API the tree calls — a newly used one would otherwise work for the author and be `undefined` on a clone.
- **CI covers both paths for free**: the `ci` job runs `npm ci` with no opt-in, so it proves the app type-checks, tests, builds and E2Es with the SDK absent; `build-and-push` proves the `withSentryConfig` path still works.

- **Init files**: [`src/instrumentation-client.ts`](src/instrumentation-client.ts) (browser), [`sentry.server.config.ts`](sentry.server.config.ts) (Node), [`sentry.edge.config.ts`](sentry.edge.config.ts) (edge) — loaded from [`src/instrumentation.ts`](src/instrumentation.ts) ahead of the reconcile loop / background watchers; `onRequestError` captures unhandled route errors; [`src/app/global-error.tsx`](src/app/global-error.tsx) catches root-layout React errors. [`next.config.js`](next.config.js) is wrapped with `withSentryConfig` (browser events tunnel through `/monitoring`).
- **Telemetry is off unless a DSN is configured**, and there is no DSN in this tree. [`src/lib/telemetry-config.ts`](src/lib/telemetry-config.ts) is the one definition all three runtimes read — pure, so the edge runtime can import it without triggering `sentry.server.config.ts`'s `Sentry.init`. Each init call is guarded on a configured DSN: `Sentry.init` with an undefined `dsn` installs the global handlers and then drops every event, which reads in a log as working telemetry. Supply `SENTRY_DSN` (server + edge, via the `console-env` ConfigMap) and `NEXT_PUBLIC_SENTRY_DSN` (browser, **inlined at build time** — a ConfigMap value cannot reach it, so browser reporting needs a build arg). For the Scality labs `isv-labs:scripts/deploy-console.sh` fills `SENTRY_DSN` at deploy. ⚠ The same DSN used to be compiled into all three runtimes with comments asking the next editor to keep the copies in sync — correct for the labs, and wrong for anyone else's build, which reported into Scality's project (ISVD-607). [`tests/unit/telemetry-config.test.ts`](tests/unit/telemetry-config.test.ts) fails on a DSN-shaped literal reappearing in any of the four files, matching the *shape* rather than the old value so another account's DSN fails it too.
- **Hardened on purpose — do not re-enable when adding signals**: no `enableLogs`, no `includeLocalVariables`, replay masking pinned (`maskAllText`/`maskAllInputs`/`blockAllMedia`, `networkDetailAllowUrls: []`). The console holds lab secrets (objectstore/S3 keys, camera-sim SSH PEM, the Firestore SA key when that backend is in use) in server locals, and renders one credential as text — the Grafana password on the overview, when `GRAFANA_PASSWORD` is set. Server locals alone justify every item above: `includeLocalVariables` would attach them to any frame that touches a secret.

  ⚠ Two further reasons used to be given here and both were false, so do not restore them from an older copy. **The Secrets page displays no value** — `GET /api/secrets/<key>` returns `{ key, configured, ageMs }` and rotation is write-only. **Nothing logs cluster command lines**: checked 2026-08-13 across all 90 `log.*` call sites, whose context keys are `err`, `pod`, `namespace`, `topic`, `count` and similar, and neither `sshExec` nor `runInPod` logs its command. The hardening stays regardless — but a justification that overstates gets discounted, which is worse than a shorter true one (ISVD-550).

- **Redaction is one definition, in [`src/lib/redact.ts`](src/lib/redact.ts), and both consumers import it**: [`error-bridge.ts`](src/lib/error-bridge.ts) before a Sentry capture, [`logger.ts`](src/lib/logger.ts) before anything reaches stdout. It has to live in its own module rather than in `error-bridge`, where it started — `error-bridge` imports `createLogger`, so the logger importing back is a cycle, and `error-bridge` also pulls in the Sentry SDK and kafkajs, which the near-universally-imported logger must not.

  `normalizeCtx` applies it to the call-site ctx **and to `baseCtx`**. That second half was the wider hole: `baseCtx` was spread raw, so a credential handed once to `createLogger` or `child` bypassed redaction on every line that logger ever wrote. `SECRET_KEY_PATTERN` is additionally tested at the top level, because `redactAndCap` only inspects key names it meets *inside* an object — a bare `{ password: "…" }` arrives as a string and only the value-shape check would see it.

  Two accepted consequences of sharing the Sentry-side helper: strings over 2000 chars are truncated, `err.stack` included (~20 frames, and it bounds the log line), and objects cap at 50 keys. `msg` is deliberately **not** redacted — it is a literal at every call site, and the value check only matches a string that *starts* with a credential, so scanning `msg` would risk blanking a message while catching almost nothing. Values belong in `ctx`.

  ⚠ Nothing was leaking when this was added — all 90 call sites were checked (ISVD-550). That is the point: the guarantee now holds for the call site nobody has written yet. [tests/unit/logger.test.ts](tests/unit/logger.test.ts) covers both paths and includes a case pinning every ctx key the tree actually logs, so a denylist widened until it eats real diagnostics fails.
- **Source maps + releases**: uploaded **inside the image's `next build`** — [`Dockerfile`](Dockerfile) takes `SENTRY_ORG`/`SENTRY_PROJECT`/`SENTRY_RELEASE` build args + `SENTRY_AUTH_TOKEN` as a BuildKit secret. Both build drivers (`isv-labs:scripts/build-console-image.sh` laptop-sideload — the path that reaches Pyramid — and [`.github/workflows/build-console.yml`](.github/workflows/build-console.yml) CI GHCR) pull `isv-labs-sentry-build-env` from Secret Manager, fail-soft. `SENTRY_PROJECT` is fixed to `scality-vss-console-ui` (the shared secret's value is the deployer's).
- **Verify**: `GET /api/sentry-verify` throws deliberately — `kubectl -n console exec deploy/console -- curl -s http://localhost:8800/api/sentry-verify`, then check the issue shows frames at `src/app/api/sentry-verify/route.ts`.
